# Rule: the legacy API

**Scope:** `packages/legacy-api/` — read before touching the hapi server.
**Backing ADR:** 0034.

It is a facsimile of a long-lived production hapi codebase, kept deliberately in that shape so the strangler campaign has something real to measure. The conventions below are the opposite of the Nest server's on purpose. Do not "improve" it toward the hexagonal layout; a module leaves this package by being rebuilt on the Nest server, never by being refactored in place.

- **What it owns.** `user`, `auth`, `organization`, `todo` and `billing` — every route in the contracts' `DomainApi` and `CliApi`, and only those. `test/route-parity.test.ts` composes the server and holds its route table to the contracts (param names aside), so a route added on one side without the other fails the unit suite.
- **Layout.** `src/application/<feature>/` holds `<feature>-routes.ts` (hapi route arrays), `<feature>-service.ts` (a class or a bag of functions with the business logic), `<feature>-model.ts` (bookshelf models) and `<feature>-access.ts` (ACL assertions). `src/lib/` holds shared helpers. `src/bin/` holds process entrypoints. `migrations/` and `seeds/` are knex, all tables in `public`.
- **Wiring is electrolyte.** A module the container loads uses `export =` so the module _is_ the factory function or class, and declares its dependencies as string ids: `factory["@require"] = ["bookshelf", "user/user-service"]`, `factory["@singleton"] = true`. A function whose name starts lowercase is called as a factory; a class (uppercase) is `new`ed. `bootstrap.ts` lists the route factories it creates. No import graph sees these edges, which is the point.
- **Language.** TypeScript compiled as CommonJS, `noImplicitAny: false`. `any`, deep relative imports and sloppy booleans are tolerated here by an override in `.oxlintrc.json`; import sorting and the correctness rules still apply.
- **Permissions leak on purpose.** `can(action, resourcePath)` pre-handlers from `src/lib/access/`, `fromOwn*`-style pre-handlers and inline role checks inside route files, one-off permission helpers. That is the smell; keep it consistent rather than fixing it.
- **Transactions** are `bookshelf.transaction(async (t) => …)` in services with `{ transacting: t }` threaded through; the wallet HTTP call sits inside one, and compensation is a best-effort delete afterwards.
- **It never imports Nest code.** Not `@org/server`, not `@org/database`, not the kernel packages; the node's allowlist refuses them in the editor and the root graph rules at check time. It shares the database and the HTTP contracts, nothing else. Its migrator owns every `public` table in `knex_migrations`; the Nest migrator keeps `wallet` in `knex_migrations_nest`, and each reset leaves the other standing.
- **The seam.** `organization-service.createOrganization` opens the wallet over HTTP inside its own transaction: a refusal rolls back and answers `502 BadGateway`; a failure after the wallet opened deletes it again. `src/lib/backend-client/` is the only file that names the Nest server's URL and the inter-service token.
- **Third parties sit behind one factory each.** `billing/stripe-gateway.ts` hands back the SDK or the in-memory stand-in on `stripe.useFake`; the webhook route takes the raw body (`payload: { parse: false }`) because the signature is over the bytes. Do not name a file `*-fake.ts`: the root manifest's orphan exemption for Nest fakes matches by basename and would drop it out of the graph scope.
- **Tests.** `*.spec.ts` beside a service are unit tests over stubs (a hand-rolled knex chain, the fake gateway, `vi.fn()` collaborators). `test/**/*.integration.test.ts` compose the real server through `test/server.ts` and drive it with `server.inject` against `DATABASE_URL_TEST`, with `test/helpers/fake-wallet-server.ts` standing in for the Nest server and `fake-idp.ts` for Zitadel; `test/setup.ts` installs the tsx require hook the container needs to load TypeScript. `test/health-check.test.ts` and `test/route-parity.test.ts` are the composed-server tests that need no database. The acceptance suite boots this server beside the Nest one and the web.
- **The mirror.** While a module is dual-written (ADR-0035, `mirrored`), its service emits a `mirrorEvents.*` server event (`src/constants/mirror-events.ts`) once the row is written, and `mirror-event-handler-plugin.ts` forwards it to the Nest module's internal API through `backend-client/domains/<module>.ts`. A failed forward is logged, never raised; the backfill squares the replica. The campaign counts a knex write whose method emits no mirror event as unmirrored.
- **The campaign's markers.** `src/application/<m>/sector.ts` is not part of the legacy shape: it is the strangler campaign's marker (ADR-0035), exporting a `sector` object that names the sector and lists what it owns on both servers. Read by the engine, never created by the container. Touching a module's folder runs you into the nudge; leave the sector no worse, and pay a holdout down in its own commit followed by `pnpm campaigns:clear`.
- **Run.** `pnpm -F @org/legacy-api dev` on `:9000`; the web proxy, the CLI and the MCP server point here. `pnpm dev` starts it with the Nest server and the web. Anything the goodbones tooling gets wrong while this package is worked on goes in `docs/plan/goodbones-findings.md`.
