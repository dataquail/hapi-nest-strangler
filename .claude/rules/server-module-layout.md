# Rule: server module layout

**Scope:** `packages/server/src/` — read before adding/moving files in a feature module.
**Backing ADRs:** 0002 (module layout), 0003 (aggregates/events), 0013 (HTTP endpoint files), 0020 (per-module DB schemas), 0022 (cross-module ports), 0023 (domain services / interface utils), 0024 (dot-delimited filenames), 0032 (module imports and exports).

Each feature module lives at `packages/server/src/modules/<feature>/` with sibling folders. There is no `application/` umbrella — commands, queries, and event-handlers are siblings, each with its own `imports` allowlist in `packages/server/architecture.yaml` (see ADR-0008, ADR-0027, ADR-0031).

- `domain/` — events, errors, ports (see `domain/ports/` below), and the DDD stereotypes below. Each stereotype carries an explicit filename suffix and a matching identifier-keyword suffix so its role is legible at a glance:
  - **Aggregate roots** — `*.root.ts`. The root data type is `XRoot` (a zod schema plus its inferred type). Operations are **pure free functions** collected into an `export const XRootOps = { … } as const` bag in `*.root-ops.ts` — the data stays a dumb value (no methods on it). Consumers `import { XRoot }` and `import { XRootOps }`. Only `*.root.ts` carries a test-parity obligation. Lifecycle default: carry state in flag/nullable columns and let each op guard its own invariants and return `Result<Outcome, DomainError>` (`oxide.ts`; `Outcome` is the op's success payload: new state + emitted events), so invariants are enforced in the domain once; model states as distinct variants unioned into `XRoot` only when states carry divergent data — see ADR-0003.
  - **Constituent aggregates** — `*.aggregate.ts` (a collection of entities/VOs that is only a _part_ of a root). No parity obligation.
  - **Entities** — `*.entity.ts`, identifier `XEntity`. **Value objects** — `*.value-object.ts`, identifier `XValueObject`. **Branded IDs** — `*.id.ts`, identifier `XId` (`z.guid().brand<"XId">()`; parse with `XId.parse(...)`).
  - **Errors / events** — `*.errors.ts` (classes extending `TaggedError("X")<Props>` from `platform/ddd/contracts/tagged-error.ts`), `*.events.ts` (`Event.make("Tag", schema)` from `platform/ddd/contracts/domain-event.ts`).
  - **Filename convention (ADR-0024):** every stereotype is a dot-delimited suffix (`.command`, `.repository`, `.handler`, …); dashes appear only _within_ a concept name (`api-token.repository.ts`, `find-users.query.ts`). Compound stereotypes keep internal dashes as one segment (`.repository-live`, `.event-adapter`, `.value-object`). There is no `.controller.ts`, `.service.ts` or `.dto.ts`.
  - **Domain services** — `*.domain-service.ts`, a pure free-function bag (like `RootOps`, not `@Injectable()`) for stateless domain logic **no single aggregate owns** (ADR-0023). Test-obligated. Guard against anemia: only for logic with no aggregate home (`CredentialHash`); logic that operates on one aggregate stays on its `RootOps`. Randomness never lives here — it stays in the command handler (the shell).
  - **Ports** — `domain/ports/`, tiered by counterpart (ADR-0022); no port sits directly in `ports/`. `ports/repositories/*.repository.ts` (own datastore), `ports/clients/*.client.ts` (true third-party systems), `ports/acl/*.acl.ts` (other bounded contexts). A port is an **abstract class** — it is both the type and the Nest injection token — exporting types beside it and never a value. The tier decides the anti-corruption obligation and, for `acl/`, which infrastructure adapter may import the module's `<feature>.imports.ts`.
- `commands/` — write-side use cases. Each has a `<verb-noun>.command.ts` declaring the message — `export class XCommand extends Command<XResult>` with `constructor(public readonly payload: XPayload)`, plus the exported `XPayload` type and the `XResult = Result<A, E1 | E2>` alias — and a `<verb-noun>.handler.ts` holding `@CommandHandler(XCommand) export class XHandler implements ICommandHandler<XCommand>`. The handler injects `UnitOfWork` and its ports by token (`@Inject(TodosRepository)`), and `execute` is `return this.unitOfWork.run<XResult>(async () => …)`. **Identifiers carry the stereotype** (ADR-0024): `CreateTodoCommand`, `CreateTodoHandler`, `CreateTodoPayload`, `CreateTodoResult`. The module's `<feature>.command-handlers.ts` lists `xCommands` and `xCommandHandlers` side by side plus the `xCommandSpanAttributes` map.
- `queries/` — read-side projections. Same `.query.ts` + `.handler.ts` split (`@QueryHandler`, `IQueryHandler`), same identifier rule (`FindUsersQuery`, `FindUsersHandler`; `.policy-query.ts` included). A query **must not** reach the write-side consistency boundary: it builds its own read model by reading SQL directly through `Database` (`@Inject(Database)`; `RowSchemas.*` from `@org/database` are the reusable read-model kernel), never by loading an aggregate through a repository. From its own `domain/` it may import only branded IDs and cross-context ACL ports; roots, ops, repositories, specifications, value-objects, errors and events are off-limits (`queries-isolation`). Read-side errors and view types live in the `.query.ts`. Joining the ambient unit-of-work transaction is automatic — the client resolves the transaction connection from `AsyncLocalStorage` before every statement and falls back to the pool when there is none — so a policy/ACL query resolved during a command's authorization is correct without an opt-in. A query published so **other** modules' authorization checks can ask it a question is `*.policy-query.ts` (ADR-0022): a cross-module contract with a stability obligation, reached by consumers only through their own `domain/ports/acl/` adapter.
- `event-handlers/` — write-side use cases (`*.handler.ts`) reacting to internal triggers (`event-handlers/triggers/<publisher>.triggers.ts`). Run in the publisher's async context and inherit its transaction (ADR-0007). Same dependency shape as `commands/`. Declared in the taxonomy; no module has one yet.
- `infrastructure/` — driven adapters, tiered by counterpart to mirror `domain/ports/` (ADR-0022); private to the module. `infrastructure/repositories/` (`*.repository-live.ts` — `@Injectable() class XRepositoryLive extends XRepository` — + `*.repository-fake.ts` + `*.mapper.ts`), `infrastructure/clients/` (third-party adapters: `*.client-live.ts` + `*.client-fake.ts` behind a `*.client.ts` port, self-contained `*.client.ts` clients, `*.email.tsx` templates), `infrastructure/acl/` (anti-corruption adapters to other modules: `*.acl-live.ts` + `*.acl-fake.ts` behind a `*.acl.ts` port — the only place, besides `interface/events/`, permitted to read `<feature>.imports.ts`). A live is bound to its port in `<feature>.module.ts` with `{ provide: XRepository, useClass: XRepositoryLive }`.
- `sagas/` — `*.saga.ts` process managers over **post-commit** events (`stream`), one per saga, each with a sibling `*.saga.test.ts`. If one event decides the outcome it is an `interface/events/` adapter instead. Bus-only like an adapter (`sagas-isolation`): own events/ids, own `*.command.ts`, the buses, `platform/ids/`, `<feature>.imports.ts` for cross-module events — no repositories, no ops, no `@org/database`. A saga has no publisher transaction to inherit, so a repository call here would write outside every unit of work. Declared; empty.
- `interface/` — inbound adapters, one subfolder per protocol:
  - `interface/http/` — one `<endpoint-name>.endpoint.ts` per HTTP endpoint (ADR-0013): a `@Controller()` class named `XEndpoint`, `@UseGuards(UserAuthGuard)`, one method decorated `@Endpoint(route)` with `route = XContract.Group.routes.<name>`, `@Caller()`, `@Param(zodPipe(route.params))`, `@Body(zodPipe(route.body))`, authorizing through `Authz.hasPermissions` and dispatching through `AppCommandBus` / `AppQueryBus`, translating each `Err` with `unwrapOrThrow(result, ProblemMap)`. `index.ts` exports the `xEndpoints` list the module registers as controllers. May also hold `*.util.ts` — pure, leaf, test-obligated protocol helpers (ADR-0023), allowed **only** in `interface/http/` and `interface/cli/`.
  - `interface/cli/` — the same shape over CLI-facing routes; `index.ts` exports `xCliEndpoints`.
  - `interface/events/` — one `<publisher>.event-adapter.ts` per upstream module whose domain events this module consumes (ADR-0007 ACL): an `@Injectable()` class implementing `OnModuleInit` that calls `this.events.subscribe(...)` / `subscribeAfterCommit(...)` on `DomainEventBus` and dispatches its own module's command. Reads foreign events from its own `<feature>.imports.ts`.
- `policies/` — `*.policies.ts` (the `@Injectable()` contribution class exposing `contribution` plus the `declare module "@org/authz/policy-registry"` augmentation and the resource-name constants), `*.resource-resolver(s).ts` (`@Injectable()` entry classes exposing `resolve`), and `is-*.policy.ts` checks (`makeIsX(port)` factories). Import `Check`, `CheckFor`, `ResourceCheck`, `CallerCheck`, `Resolver`, `PolicyContribution` from **`@/platform/auth/authz.js`**, never from `@org/authz` directly — that file carries the `AuthzConfig` augmentation, and the type-aware linter only sees an augmentation through a file's own import graph. A check takes its data source as an argument and the contribution closes over the module's own ACL ports, so every registered check is fully closed. Policies read **read models only** — never a root, repository, or specification (`policies-isolation`). The contribution and resolver entries are providers the module `exports`; `AuthzModule` folds them.
- **Module root** — a closed set of aggregation/composition files only, each named for the plane it serves (ADR-0024): `<feature>.platform.ts`, `<feature>.exports.ts`, `<feature>.imports.ts`, `<feature>.module.ts`, `<feature>.command-handlers.ts` / `<feature>.query-handlers.ts`, `<feature>.event-span-attributes.ts`, `<feature>.handlers.test.ts`. There is no `index.ts`. Any other file must move into a subfolder — enforced by `architecture/structure`.
  - `<feature>.module.ts` exports one `@Module` class, `<Feature>Module`: `imports` names the `<feature>.module.ts` of every module this one reaches through an ACL port; `controllers` are the endpoint lists; `providers` are the handlers, the port→live bindings, the event adapters, the policy contribution and resolver entries; `exports` are what a peer's providers or the platform's registries need (contribution, resolver entries) — never a repository.
  - **A module states its own imports by importing them** (ADR-0032). Nest `imports` is a private import — a provider role exports is visible to todos' providers and to nobody who imports todos — and `exports` is the re-export. There is no ordering anywhere: `AppModule` lists every module once, and a forgotten import fails at bootstrap naming the provider and the module.
  - **Each plane has one gateway in and one out, and they do not mix.** On the coupling plane, `<feature>.exports.ts` publishes and `<feature>.imports.ts` consumes: the message classes a peer may construct, the domain events it reacts to, the errors it must translate. It is the only file that may name another module's vocabulary, so an ACL adapter and an event adapter read their own module's gateway. On the wiring plane, `<feature>.module.ts` names other modules' `<feature>.module.ts`. A Nest module class never appears on a coupling file. `<feature>.platform.ts` is the PLATFORM surface — the module class, `xCommands`/`xQueries` and their span-attribute maps, the event span attributes, the policy contribution and resolver entries, and for billing the live/fake gateway pair — reachable only from `@/platform/**`, `@/test-utils/**`, `main.ts` and tests; no module may name another module's.
  - **What the peer surface declares is named `<module>Access<Queries|Commands|DomainEvents|Errors>`** — `roleAccessQueries`, `userAccessCommands`, `organizationAccessDomainEvents`, `userAccessErrors` — enforced by `architecture/surface` on `<feature>.exports.ts`. Events and errors are collected into objects; the surface may not re-export at all; a peer that needs a type takes it off the published value (`InstanceType<typeof userAccessErrors.UserAlreadyExists>`). Publish nothing without a consumer. Because `@nestjs/cqrs` has one bus, the grant is the import: a peer cannot dispatch a message class it cannot import (ADR-0006).
  - **A real cross-module cycle is an ES module cycle** (`import/no-cycle`, `no-cycles`) or a Nest module cycle, which Nest reports at bootstrap. `forwardRef` is forbidden; a cycle is a design error.
  - **A service whose adapter differs between composition roots is the root's to provide.** Billing's `BillingGateway` is the only one: `BillingGatewayModule` (`platform/modules/`, `@Global()`) provides Stripe, the test root overrides the token with the fake. The billing module lists neither.

Cross-module access leaves through `<feature>.exports.ts`, which may not re-export from `infrastructure/` or `interface/`, and arrives through the consumer's `<feature>.imports.ts`. The published surface is domain types (events, IDs, errors) and message classes — never a Nest module or a provider.
